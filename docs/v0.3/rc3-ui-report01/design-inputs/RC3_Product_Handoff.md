## 4. مرزهای هماهنگی و پذیرش
این صورت‌بندی‌ها تحت اختیار D03-002 برای حفظ هدف و جلوگیری از برداشت ناخواسته‌اند:
- مرجع رفتار: تصمیم Product و اسناد رفتاری بسته؛ تایپوگرافی و ابعاد از normalization؛ تصویر مرجع ترکیب‌بندی است.
- M-01 قدیمی هنوز «فعالیت‌ها و پارتو» دارد؛ برای بخش خلاصه، متن M-04 مقدم است. تفاوت ترتیب ناوبری پایین تصاویر، مجوز بازچینی خودکار همهٔ تب‌ها نیست؛ الگوی یکپارچهٔ جاری حفظ و با UX هماهنگ شود.
- در M-10 حذف کارت‌های «یادآوری بعدی»، «بازه جاری»، «آخرین بازه تکمیل‌شده» فقط حذف نمایش مستقل آن‌هاست. اگر مسیر ثبت در یکی از آن‌هاست، اقدام معادل روشن در طرح امروز باقی بماند؛ نبود دکمه در PNG مجوز حذف ثبت نیست.
- در timeline، دادهٔ واقعی ثبت‌شده و بازهٔ جاریِ ثبت‌نشده متمایز باشند. متن نمونهٔ «در حال انجام» نباید از آخرین فعالیت گذشته استنتاج شود.
- dayProgress نمایانگر زمان سپری‌شده از روز تنظیم‌شده است، نه بهره‌وری یا درصد ثبت. شمع و Donut با یک مبنا و مقدار محدود به ۰..۱ نمایش داده شوند.
- زمان قبل/بعد روز تنظیم‌شده، شروع/پایان برابر یا عبور از نیمه‌شب، تغییر timezone و بازگشت از پس‌زمینه باید بر قرارداد موجود RC2/ADR روز تکیه کنند؛ سیاست جدید روز از روی تصویر حدس زده نشود. تنظیم نامعتبر نباید division-by-zero بسازد. ابهام واقعی ابتدا در Implementation بررسی و فقط مسئلهٔ حل‌نشده ارجاع شود.
- به‌روزرسانی progress در foreground در حد دقیقه کافی است؛ برای حرکت شمع alarm یا سرویس دائمی پس‌زمینهٔ تازه ساخته نشود.
- پیام «عالی پیش می‌روی» نمونه است و ارزیابی تأییدشده نیست؛ تا تعریف signal معتبر، از متن خنثی مانند «امروزت را مرور کن» استفاده شود. سبز گذر زمان نشان‌دهندهٔ خوب‌بودن فعالیت نیست.
- صدا/لرزش تنظیمات موجود در M-02 حفظ شود؛ feedback احساسی جدید، دسته‌بندی روز خوب/بد و motion پیچیده فعلاً Deferred هستند. state شمع با زمان واقعی در Scope است.
- توکن رنگ و دارایی تولیدی شمع/تصویر هدر باید تکمیل شوند؛ ZIP فعلی PNG موکاپ دارد و فونت، تصویر هدر مستقل یا شمع آمادهٔ اجرا ندارد. Codex نباید کل عکس صفحه یا متن رندرشده را UI برنامه کند. بازنمایی سبک و مقیاس‌پذیر شمع و دارایی مجاز هدر با UX هماهنگ شود.
- chip بصری 40dp یا دکمهٔ 44dp فقط با سطح لمس حداقل 48dp؛ تضاد ظاهری normalization با touch target این‌گونه حل شود.
- D03-004، قرارداد روز ADR-003-04 و آیکون ADR-003-05 حفظ شوند؛ تغییر دیتابیس، ICATUS یا scheduler برای ظاهر UI مجوز ضمنی ندارد.

## 5. خارج از این افزایش دامنه
تحلیل/قضاوت فعالیت مفید، مدل احساسی مثبت/منفی، اهداف و mood، feedback صوتی/لمسی جدید و motion تعریف‌نشده؛ بازنویسی اعلان یا مدل داده؛ افزودن حالت گزارش غایب در سورس صرفاً به دلیل حضور در PNG. در صورت اختلاف دربارهٔ وجود قابلیت، Codex فایل/تابع و اثر را گزارش کند؛ قابلیت موجود حذف نشود.

## 6. تحویل و شواهد پذیرش
دفتر اجرا از Codex بخواهد:
1. HEAD، branch، وضعیت working tree و نسبت با commit RC2 را ثابت کند؛ از v0.2 دوباره شروع نکند و تغییرات جدیدتر را حذف نکند.
2. جدول طرح → screen/component واقعی → تغییر لازم → تست/تصویر تهیه کند. نام فایل‌ها اینجا حدس زده نشده است.
3. UI را مرحله‌ای اجرا کند: مبنای بصری، M-01/M-04، M-02، سپس M-10؛ ترتیب قابل تعدیل فنی است.
4. تست‌های مرتبط گزارش/زمان/تنظیمات، typecheck و smoke مسیر اعلان→ثبت و گرید را اجرا کند؛ نتیجه Pass/Fail/Not run باشد.
5. اسکرین‌شات واقعی هر چهار حالت با تاریخ/دادهٔ مشخص و مقایسهٔ مرجع؛ متن بزرگ/RTL و empty/error را بررسی کند. یک build موفق شاهد تطابق بصری نیست.
6. APK RC3 با همان applicationId و هویت امضا، versionCode بزرگ‌تر از مقدار نصب‌شده (RC2=4؛ رقم نهایی پس از بررسی build history) بسازد؛ commit، checksum، شواهد امضا، build log پالایش‌شده و known issues تحویل دهد.
7. ارتقای بدون uninstall/reset و حفظ داده، تست دستگاه و رگرسیون اعلان همچنان لازم‌اند. عدم آزمون گوشی شفاف بماند؛ به‌معنی توقف همهٔ کارهای UI نیست.
8. بررسی OI-P01/اعلان که سند مرکزی قدیمی باز نگه داشته با شواهد جدید تعیین تکلیف شود؛ RC3 UI نه رفع آن را ثابت می‌کند نه پذیرش خودکار انتشار است.
